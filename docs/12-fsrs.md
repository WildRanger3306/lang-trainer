# FSRS — требования

Статус: **реализовано** (§012). Код: `app/scheduler.py` + пакет `fsrs`.

Сейчас в продукте FSRS (пакет `fsrs`, py-fsrs). Прежний упрощённый Anki — [10-anki.md](10-anki.md), только для истории.

## Зафиксировано

### 1. Кнопки тренировки

Сразу **4** оценки (не маппинг 2→Again/Good):

| UI | FSRS Rating |
|----|-------------|
| Снова | Again |
| Трудно | Hard |
| Хорошо | Good |
| Легко | Easy |

«Не помню» / «Помню» уходят из тренировки.

### 2. Миграция существующего прогресса

**Грубая конвертация** `interval_days` / `ease` → приблизительные stability / difficulty (и state Review, due сохранить где возможно).

- Неточно, но очередь и «зрелость» не обнуляются.
- Точная формула конвертации — при реализации (зафиксировать в коде + комментарии / тесты).
- Лог `card_reviews` сохраняем; старые `remembered` bool остаются как история.

### 3. Оценка знаний (Assess)

Оставить **отдельный триаж как сейчас** (не FSRS на первом вводе):

| Вердикт | Поведение |
|---------|-----------|
| Знаю | due +7 дней, interval 7 |
| Сомневаюсь / Не знаю | due завтра, interval 1 |

Квоту новых не жжёт (`introduced_via = assess`).  
Дальше карточка живёт в **тренировке по FSRS** (4 кнопки).

### 4. Desired retention

**90%** (дефолт FSRS/Anki). Константа в коде; UI настройки пока нет. Optimizer — не в этой волне.

### 5. «Снова» в сессии

Как сейчас с «Не помню»: **Снова** → карточка **в конец очереди сегодня** + due по FSRS.  
Hard / Good / Easy — только due по FSRS, без возврата в очередь.

### 6. Гранулярность due

Оставить **календарный день** (`due_on`).  
Короткие learning-интервалы FSRS (минуты) **округлять** до сегодня / завтра (или следующего календарного дня). UI и очередь сессии без «через 10 минут».

### 7. Fuzz

**Включить** (дефолт FSRS) — небольшой разброс интервалов, меньше пиков due в один день.

### 8. Веса модели

Одни **дефолтные** параметры FSRS на весь инстанс (все пользователи).  
Хранения per-user \(w\) и UI калибровки в MVP нет.

## Бэклог (не MVP)

- **Optimizer** — подгонка \(w\) (сначала глобально или per-user) по логу `card_reviews`, когда накопится достаточно train-оценок.
  Отложено 2026-09-26: на 26.09 всего 1681 оценка за 13 дней, повторных 692, из них через ≥ 7 дн только 75; «Легко» ≈ 50%. Вернуться, когда ≈ 3000 оценок и ≈ 1000 повторов через ≥ 7 дн (примерно конец ноября); сначала read-only отчёт (обучить параметры, сравнить с дефолтом на отложенной части), включать только при стабильном выигрыше. Проверить, тянет ли `fsrs.optimizer` лишние пакеты (torch) в образ.
- Per-user веса / desired retention в UI.
- Hard/Easy подсказки «следующий интервал» на кнопках (как в Anki).

## Данные (ориентир к реализации)

`card_progress`: stability, difficulty, state, last_review; `due_on` (день); убрать опору на ease (или оставить deprecated до миграции).  
`card_reviews`: rating FSRS (1–4) + сохранить совместимость со сводкой (`remembered` = не Again, или пересчёт again_rate).

Конвертация: interval/ease → S/D при миграции БД.
